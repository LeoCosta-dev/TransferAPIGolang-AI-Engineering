# Account Service Requirements

## Purpose

The Account Service is responsible for managing customer accounts and their balances.

It is the single source of truth for account registration, account status, and account balance.

The service must expose an HTTP API for account management and balance operations.

## Functional Requirements

### Account Creation

The service must allow the creation of a new account.

An account must contain:

* a unique UUID identifier;
* a non-empty customer name;
* a non-empty customer document;
* balance;
* status;
* creation timestamp;
* last update timestamp.

New accounts must start with:

* status `ACTIVE`;
* balance `0`.

The account identifier must be a UUID generated by the service.

The document is a textual customer identifier and must uniquely identify an account.
CPF/CNPJ-specific validation is not required.

The name and document are required and must not be empty.

The service must reject the creation of an account when the document is already associated with another account.

### Account Retrieval

The service must allow an account to be retrieved by its identifier.

A successful retrieval must return the account's current state.

When the requested account does not exist, the service must return the documented not-found response.

### Account Update

The service must allow modification of account data that is explicitly marked as mutable by the API contract.

Immutable account attributes must not be changed through update operations.

Updating an account must update its modification timestamp.

An update must not unintentionally modify the account balance or status unless explicitly allowed by the API contract.

### Account Status

An account has one of the following statuses:

* `ACTIVE`;
* `BLOCKED`;
* `CLOSED`.

The service must enforce the rules associated with each status.

Status transitions must be explicit and must follow the domain rules defined in `domain.md`.

The service must reject invalid status transitions.

An account may transition to `CLOSED` only when its balance is zero.

### Balance Retrieval

The service must allow the current balance of an account to be retrieved independently from the complete account representation.

The returned balance must reflect the current persisted value.

### Credit Operation

The service must allow money to be credited to an account.

A credit operation:

* must target an existing account;
* must contain a positive monetary amount;
* must increase the account balance by exactly that amount;
* must be atomic;
* must preserve the account's domain invariants;
* must update `updated_at` after the balance change is successfully persisted.

Credit operations must respect the account status rules defined in `domain.md`.

### Debit Operation

The service must allow money to be debited from an account.

A debit operation:

* must target an existing account;
* must contain a positive monetary amount;
* must not allow the account balance to become negative;
* must decrease the account balance by exactly that amount;
* must be atomic;
* must preserve the account's domain invariants;
* must update `updated_at` after the balance change is successfully persisted.

Debit operations must respect the account status rules defined in `domain.md`.

### Idempotency

Money movement operations must support idempotent requests.

Clients must provide an `Idempotency-Key` header.

Idempotency is scoped to an account and an operation type (`credit` or `debit`).
Within the same account, a key cannot identify different operation types.

When the same idempotency key is submitted again for the same account, operation
type, and equivalent payload, the service must not apply the monetary operation
more than once and must return the original result.

When the same key is submitted for the same account with a different payload or
different operation type, the service must return a conflict.

If the first attempt fails because of a business rule before producing a
monetary effect, the key must not be retained and a later valid attempt may use
the same key.

The service must define and consistently enforce the behavior for:

* repeated requests with the same key and equivalent payload;
* repeated requests with the same key and a different payload;
* concurrent requests using the same key.

The detailed HTTP contract is defined in `api.md`.

## Validation Requirements

The service must validate all externally supplied input.

Validation must occur at the system boundary before executing the corresponding business operation.

At minimum, the service must validate:

* required fields;
* field formats;
* field lengths;
* monetary amounts;
* account identifiers;
* account status values;
* request headers required by the API contract.

Invalid input must not modify persisted state.

## Persistence Requirements

Account state must be persisted durably.

The Account Service uses SQLite for local development and testing.

The database must preserve the domain invariants defined by the service.

Operations that modify balance or other related state must be atomic.

Concurrent operations must not cause:

* lost updates;
* duplicated operations;
* negative balances;
* inconsistent account state.

Database-specific implementation details must remain isolated from the domain layer.

## Error Handling Requirements

Failures must be represented consistently.

Error responses must use the following JSON structure:

```json
{
  "error": "Descrição detalhada do erro em português"
}
```

The service must use appropriate HTTP status codes for:

* invalid requests;
* nonexistent resources;
* business rule violations;
* conflicts;
* unexpected internal failures.

The exact status mapping is defined in `api.md`.

Error messages exposed through the API must be written in Portuguese.

Internal implementation details must not be exposed to API clients.

## Consistency Requirements

A successful balance operation must leave the account in a valid state.

If an operation fails, the persisted account state must remain unchanged.

Balance changes must be atomic and must not expose intermediate states.

The service must not return a successful response before the corresponding state change has been successfully persisted.

## Availability and Lifecycle

The service must provide a health endpoint suitable for local development and operational checks.

The service must start successfully when all required configuration is available.

The service must fail clearly when required configuration is invalid or unavailable.

The service must support graceful shutdown.

Graceful shutdown must allow in-flight requests and persistence operations to complete within the configured shutdown period.

## Observability

The service should provide sufficient logs to diagnose operational failures.

Logs must not expose:

* credentials;
* authentication tokens;
* secrets;
* sensitive personal information.

Health and operational information should be exposed through appropriate service mechanisms without changing business behavior.

## Testing Requirements

The implementation must include automated tests covering the documented behavior.

Tests must cover at minimum:

### Account lifecycle

* account creation;
* duplicate document rejection;
* account retrieval;
* account update;
* valid status transitions;
* invalid status transitions.

### Balance

* initial balance;
* credit;
* debit;
* insufficient balance;
* invalid monetary amounts;
* blocked account behavior;
* closed account behavior.

### Idempotency

* first request execution;
* repeated request with the same key;
* same key with a different payload;
* same key with a different operation type for the same account;
* reuse of a key after a business-rule failure without monetary effect;
* concurrent requests using the same key.

### Persistence and concurrency

* atomic balance changes;
* concurrent credits;
* concurrent debits;
* concurrent credit and debit operations;
* prevention of negative balances.

### HTTP API

* successful responses;
* validation errors;
* not-found responses;
* business rule errors;
* conflict responses;
* unexpected internal errors.

Tests must verify observable behavior and must not depend unnecessarily on implementation details.

## Acceptance Criteria

The Account Service is considered complete when:

1. all functional requirements are implemented;
2. all domain invariants are enforced;
3. the HTTP API matches `api.md`;
4. persistence behavior matches the documented requirements;
5. idempotency is correctly enforced;
6. concurrent balance operations preserve consistency;
7. required automated tests pass;
8. `go vet` passes;
9. race detection passes for concurrency-sensitive behavior;
10. the implementation is formatted with `gofmt`;
11. documentation remains consistent with the implementation.
